# Adding height data to improve the detection of seedlings using Faster-RCNN

This project tests whether adding a height map (a canopy height model, or CHM) to RGB drone images helps a
[Faster-RCNN](https://arxiv.org/abs/1506.01497) object detector find seedlings.
Each sample is a 256×256 RGB tile paired with a single-channel height tile covering the same area. The seedlings are
labelled with bounding boxes.

## Model variants

The variants differ in where the height data enters the network:

| Name        | Where the height data enters                                                                                  |
|-------------|---------------------------------------------------------------------------------------------------------------|
| **Vanilla** | It doesn't. This is the unmodified torchvision Faster-RCNN, used as the baseline                              |
| **First**   | As a fourth input channel to the first convolutional layer of the backbone                                    |
| **Final**   | After RoI pooling, just before the final dense classification and bounding box regression heads               |
| **Pre-RoI** | Concatenated to the backbone feature maps after the region proposal network (RPN), before RoI pooling         |
| **Pre-RPN** | Concatenated to the backbone feature maps before both the RPN and RoI pooling                                 |

Every variant uses a ResNet-50 backbone with a feature pyramid network. Where it makes sense, each variant is built
three ways: fully COCO-pretrained, with an ImageNet-pretrained backbone only, or trained from scratch.

## Project structure

```
├── data/                    # Not tracked in git (see "Data" below)
├── models/
│   ├── configs/             # Experiment config files (YAML)
│   ├── templates/           # Untrained template models, generated by src/main.py
│   └── trained/             # Trained models (.pt), their configs (.yaml) and logs
├── notebooks/               # Analysis of experiment results, named by date (dd_mm_yy)
└── src/
    ├── main.py              # Entry point: builds the templates, then runs the experiments in a config file
    ├── data/
    │   ├── tiling.py        # Aligns, resizes and tiles the raw orthophotos and height maps
    │   ├── make_test_train.py   # Matches tiles to labels and writes the train/test split CSVs
    │   ├── data_classes.py  # SeedlingDataset: the PyTorch dataset of (RGB, height, boxes) samples
    │   └── apply_model.py   # Runs a trained model over tiles and writes predictions as Pascal VOC XML
    ├── models/
    │   ├── make_base_models.py  # Builds and saves the template model for each variant
    │   ├── modifications.py     # Modified torchvision Faster-RCNN / RoI-head classes that accept height input
    │   └── train_model.py       # Training loop, validation, early stopping and mAP evaluation (pycocotools)
    ├── analysis/
    │   └── analysis_functions.py  # Pulls run results from MLflow into pandas for the notebooks
    ├── util/                # Shared helpers and a script that computes per-channel image statistics
    └── tests/               # unittest tests
```

## Installation

```shell
pip install -r requirements.txt
```

GDAL is only needed for the tiling step (`src/data/tiling.py`), and it needs the system GDAL libraries installed
first. A CUDA-capable GPU is strongly recommended for training.

## Data

The data isn't included in the repository. The scripts expect this layout under `data/`:

- `data/raw/images/`: full-size orthophotos (`site_<lane>_201710_030m_ortho_als11.tif`) and height maps
- `data/raw/labels/`: bounding box labels for each tile, in Pascal VOC XML format
- `data/interim/`: intermediate files written by the tiling script
- `data/processed/`: the final 256×256 RGB and height tiles

The data pipeline has two steps:

```shell
# 1. Align the height maps with the orthophotos and cut both into tiles in data/processed/
python3 -m src.data.tiling

# 2. Match tiles to labels and write the train/test CSVs to data/
python3 -m src.data.make_test_train
```

`make_test_train` drops tiles that are mostly white (empty), then writes five train/test splits for
cross-validation. Each split comes in several versions with different ratios of negative tiles (tiles with no
seedlings) to positive tiles. Each CSV row gives the paths to a tile's RGB image, height image and label file.

The input file paths are currently set inside the scripts themselves.

## Running experiments

Each experiment is described by a YAML config file in `models/configs/`. **Every value is a list.** `src/main.py`
trains and tests one model for every combination in the cartesian product of the lists, so a config such as

```yaml
'base_model_path': ["models/templates/A.pt", "models/templates/B.pt"]
'learning_rate': [2.0e-3, 2.0e-4]
'seed': [1, 2]
```

runs 2 × 2 × 2 = 8 trainings. To run one or more config files:

```shell
python3 -m src.main models/configs/21_06_17_first_test_long_cv2.yaml
```

For each run, the script:

1. Rebuilds the template models in `models/templates/`.
2. Skips any combination whose config matches one already saved in `models/trained/`.
3. Trains with early stopping on the validation loss and keeps the epoch with the best validation mAP.
4. Evaluates that model on the test set.
5. Logs parameters and metrics to MLflow, and writes the model, its config and a log file to `models/trained/`.

These are the main config keys:

| Key                                    | Meaning                                                                            |
|----------------------------------------|------------------------------------------------------------------------------------|
| `data_file`                            | Dict with `train_file` and `test_file` CSV paths (older configs use these as separate keys) |
| `train_neg_ratio` / `test_neg_ratio`   | Negative-to-positive tile ratio; picks the matching CSV version                    |
| `base_model_path`                      | Template model in `models/templates/` to start from (this sets the variant)        |
| `task_name`                            | MLflow experiment name, also used in the output filenames                          |
| `optimiser`, `learning_rate`, `momentum`, `weight_decay` | Optimiser settings                                               |
| `epochs`, `patience`                   | Maximum epochs, and epochs without improvement before early stopping               |
| `clip`                                 | Gradient-norm clipping value (optional)                                            |
| `valid_ratio`                          | Fraction of the training data held out for validation                              |
| `seed`, `device`                       | Random seed and torch device (e.g. `cuda:0`)                                       |
| `develop`                              | If `True`, errors stop the run and the trained model isn't saved                   |

The files in `models/configs/` are named by date (`yy_mm_dd`) and are a record of the experiments that were run.
They're useful as examples.

> **Note:** the MLflow tracking server URI is currently hard-coded in `src/main.py` and
> `src/analysis/analysis_functions.py`, so it needs to be edited there before running.

## Analysing results

The notebooks in `notebooks/` load the run data from MLflow and from `models/trained/` using the helpers in
`src/analysis/analysis_functions.py`, then plot losses, mAP and comparisons between variants. Start Jupyter from
the `notebooks/` directory so the notebooks can find the `src` package.
